## P1 — серьёзно

- [ ] **Проверить остальные RSC-границы на несериализуемые пропсы.**
  По аналогии с P0-багом: пройти все `app/**/layout.tsx` и серверные страницы,
  которые передают массивы конфигов/колбэки в клиентские шеллы
  (`DashboardShell`, табличные обёртки, тулбары). Цель — убедиться, что через
  границу идут только сериализуемые данные. Точечный греп: серверные файлы,
  где в объект-проп кладётся стрелочная функция или `() =>`.

- [ ] **Крупные файлы-компоненты — риск и для перфа, и для поддержки.**
  Разбить на под-компоненты/хуки:
  - `components/admin/overview/source-detail-dialog.tsx` — **1043 строк** (крупнейший в проекте).
  - `components/admin/secret-transfer-tab.tsx` — 752.
  - `components/manager/inbox/message-composer.tsx` — 766 (горячий путь, ремаунтится часто).
  - `components/admin/secret-telegram/personal-messenger.tsx` — 662.
  - `components/admin/god-messenger/use-god-composer.ts` — 657.
  - `components/buyer/source-detail.tsx` — 629.
  Крупный клиентский компонент = больше JS в бандле и тяжелее ре-рендер.
  Приоритет — composer (горячий) и source-detail-dialog (самый большой).

- [x] **`lib/db.ts` пул + SSE — проверено, давление НЕ создаётся.**
  Разобрано вручную: SSE-роуты (`/api/stream` и др.) НЕ берут соединение из
  основного пула — они подписываются на общий realtime-хаб (`lib/realtime.ts`),
  который держит ЕДИНСТВЕННЫЙ выделенный `pg.Client` (не из пула) на весь
  процесс и раздаёт события всем подписчикам. gap-recovery (`getMessagesSince`)
  бьёт в пул разово при реконнекте, не держит соединение. Сам пул образцовый:
  `statement_timeout` (30с), slow-query лог (`DB_SLOW_QUERY_MS`), сохранение
  `.code` из PG-ошибки (нужно для 23505/42P01), `connectionTimeoutMillis`.
  Realtime-хаб: keepalive-пинг (30с) против «мёртвого TCP», backoff-реконнект,
  synthetic `resync` после переподключения. Вывод: пул НЕ голодает от SSE.

## P2 — заметно

- [ ] **Структурное дублирование трёх «console»-стеков.**
  `lib/ai-console/` (15 файлов), `lib/admin-console/` (21), `lib/servers-console/` (8)
  повторяют один скелет: `assistant.ts / intents.ts / prompt.ts / run-assistant.ts /
  run-state.ts / tools-*.ts`. Домены разные (настройки ИИ-продавца / общий
  админ-ассистент / серверы-деплой), и общий низкоуровневый слой уже вынесен в
  `lib/console-core/`. Это НЕ копипаста, а повтор каркаса раннера.
  Предложение: вынести в `console-core` обобщённый «tool-loop runner» +
  типы `RunState<TPanel, TAction>` и `finalize`, чтобы три стека делили один
  движок, а различались только каталогом интентов, промптом и набором тулов.
  Аналогично — 4 SSE-роута (`ai-console`, `console`, `servers-console`,
  `wijegniwjgwjog` — 85–136 строк каждый) почти идентичны: вынести общий
  `createRealtimeSseStream({ guard, filter })` хелпер и оставить в роутах
  только гейт+фильтр.

- [ ] **~77 неиспользуемых экспорт-функций и 114 неиспользуемых экспорт-типов (knip).**
  Не мёртвые файлы, а «публичные» экспорты, которые никто не импортирует
  (напр. `deleteFinanceEntry` в `lib/finance/resources.ts` и десятки типов).
  Пройти список knip и: либо убрать экспорт (сделать локальным), либо удалить,
  либо (если это осознанный публичный API) добавить в `knip.json` ignore.
  Полный список — `pnpm exec knip --reporter symbols`.

- [ ] **Мессенджер-компоненты: три похожих «message-bubble/thread-pane».**
  `components/admin/god-messenger/*`, `components/admin/secret-telegram/*`,
  и `components/shared/inbox/*` — три реализации пузыря/треда. Инбокс
  менеджера/куратора уже объединён через shared; god-messenger и
  secret-telegram живут отдельно (god-синтетика/личный ТГ админа — другой
  контракт). Проверить, можно ли `message-bubble` и медиа-плитки свести к
  одному презентационному компоненту с пропсами, оставив различия в данных.

- [ ] **`lib/data/` — 91 файл, `app/actions/` — 58.** Большая поверхность.
  Проверить на дублирующиеся хелперы (напр. форматирование МСК-времени,
  нормализация контактов, скоуп-по-роли), которые могли разойтись копиями.
  Кандидаты на общий модуль: скоуп-хелперы `userId/curatorId/buyerId` в
  запросах — убедиться, что это один хелпер, а не N вариантов.

## P3 — долг/косметика

- [ ] **`knip.json` содержит устаревшие/избыточные записи** (knip сам ругается
  на redundant entries). Почистить конфиг.
- [ ] **`.env.example` — 179 строк.** Свериться с реально читаемыми `process.env.*`
  по коду: убрать мёртвые переменные, добавить недостающие обязательные.
- [i] **Дубль номера миграции `154`** — два файла: `154_backfill_god_synthetic.sql`
  и `154_realtime_message_contact_name.sql`. Проверено: раннер (`scripts/migrate.mjs`)
  трекает по ИМЕНИ ФАЙЛА (PK `filename` + checksum + advisory-lock + транзакция
  на файл), а не по номеру, и сортирует `localeCompare({numeric})` — оба
  применяются отдельно и по порядку (backfill → realtime). Функционально
  безопасно, но номер вводит в заблуждение при чтении истории. Оставить как есть
  (переименование сломало бы checksum-трекинг уже применённых миграций на проде).
- [i] **13 файлов хардкодят `'Europe/Moscow'` мимо `lib/time.ts`** — проверено,
  это НЕ дубль. `lib/time.ts` — слой клиентского форматирования (`formatMsk*`,
  `mskDayKey`); прямые использования — это либо SQL-day-math (`AT TIME ZONE`
  в `lead-stats`/`analytics`), либо настраиваемый per-rule/per-source часовой
  пояс с фолбэком (`tz || 'Europe/Moscow'` в `offhours`/`autopilot`/`ai-followup`),
  либо doc-комментарий. Общий модуль-константу `APP_TIME_ZONE` можно точечно
  переиспользовать в паре мест, но крупной дедупликации тут нет.
- [ ] **Единичные `console.*` в компонентах** (`shared/inbox/use-message-actions.ts`,
  `admin/god-messenger/use-god-thread.ts`, `admin/accounts-table.tsx`,
  `shared/avatar-picker.tsx`, `manager/inbox/media-selection.tsx`) — заменить на
  `[v0]`-префикс либо убрать, если это не намеренное прод-логирование ошибок.
